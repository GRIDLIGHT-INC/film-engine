# Native Instruments and Sample-Library Integration for Film Engine Music

Research brief. Written 2026-09-10 against branch `ship-001-conform-contract`. Every URL below was checked on that date unless a different date is given. Nothing in this document changes code; it extends [`music-workstation-and-ableton.md`](music-workstation-and-ableton.md) and [`music-workstation-research-brief.md`](music-workstation-research-brief.md), which cover the DAW round trip and the score-session model, and are not repeated here.

## Answer

**Possible — in one sense only, and that sense is not the one the question implies.** Native Instruments exposes no API of any kind: no REST endpoint, no SDK that renders audio, no way to ask Kontakt for a sound from outside a plugin host. NKS is a preset-metadata and hardware-mapping partnership for people *selling* instruments; Native Access is a licensing installer with a GUI; KSP is a scripting language that runs *inside* an instrument. The only way to make a Kontakt library produce audio for Film Engine is the way a DAW does it — load `Kontakt.vst3` (or the AU) in a plugin host, feed it MIDI, and bounce. That is a real and well-trodden mechanism, and it needs two things Film Engine does not have today: **notes** (the current generator returns finished audio from a prose prompt; there is no MIDI anywhere in the codebase — verified by grep, zero hits for `midi`, `kontakt`, `vst`, `nks`, `osc`, `sfz`, `soundfont` in `backend/` and `src/`), and **a renderer** (an external process that hosts plugins, which is a bigger and more fragile dependency than `ffmpeg-static`). **Recommendation:** do not build a Kontakt integration first. Build the half that is free and consistent with MCP-first — the agent writes MIDI from the existing `music_brief`, Film Engine stores it as an asset — then render it locally through an open SFZ/SoundFont synthesizer declared the way ffmpeg is, using CC0/MIT orchestral libraries. That gives a director editable notes, a per-second cost of zero, and licensing with no film/TV asterisk, and it is the exact precondition a Kontakt host would need anyway. Add a VST3/AU host for Kontakt only if the MIDI-from-agent path proves musically usable on the 30-second fixture — and if it does not, no amount of Kontakt would have saved it.

Three consequences for this question:

1. **The instrument list is decorative.** `instruments: ['solo cello', 'brushed kit']` is text in a 600-character prompt. A sample library cannot be pointed at it because there are no notes for a sample library to play.
2. **Length is already solved and must be kept.** `cueSeconds` (`scene-score.js:226`) walks cue → footage → dialogue → default and names its source. Any MIDI path has to produce a file of exactly that length or say why not, the way `sectionFit` (`music-sections.js:191`) reports rather than corrects.
3. **The asset registry cannot take a `midi` type in place.** `film_assets.asset_type` is a CHECK (`backend/db/migrations/015_film_assets.sql:10`) and the 3D work already recorded that SQLite cannot widen it (`042_threed_generation.sql:11`: stored as `other` with `metadata.kind`). A MIDI asset would follow that precedent, not a new CHECK.

The backend has exactly two dependencies, `better-sqlite3` and `ffmpeg-static` (`backend/package.json`), and `ffmpeg-static` is the declared exception to [ADR-002](../adr/002-vanilla-http-no-framework.md) — resolved as a floor, not a default, through `resolveFfmpeg()` (`backend/lib/ffmpeg.js:51-88`: `FFMPEG_PATH` → `PATH` → bundled). That resolver is the shape any new binary would copy.

## Where the notes come from

A sample library plays MIDI. Film Engine's generator emits audio. So the first architectural fact is that a Kontakt path is a *different generator*, not a different provider for the existing one, and its input has to be produced by something.

| Source of MIDI | Fit with Film Engine | Evidence |

Two facts cut across every Kontakt row:

- **Native Access is a GUI on a licensed Mac.** Libraries are activated per machine through a signed-in installer; there is no headless activation and the EULA's three-device rule applies. A render box is therefore *this* Mac, not CI and not a container. The Ableton brief already accepted the same constraint for Live ("what constitutes an acceptable real-Live smoke environment"); it is stronger here because the render itself, not just a round trip, needs the licensed host.
- **Kontakt's VST3 offline-bounce behaviour is the documented weak point**, in REAPER and in JUCE hosts alike. A headless render that comes back with stuck or truncated notes and no error is exactly the class of silent failure `AUDIO_LANES` and the −91 dB stitch exist to catch; any Kontakt path would need a volume-and-duration check on the rendered file, never a "did a file appear" check.

## Recommendation

**Phase 1 — notes exist (free, MCP-first).** Add `music_midi_write`: the agent reads `music_brief` (already built, already free) and returns a neutral note list — tracks with an instrument name and General MIDI program, tempo, and notes as `{start_ms, duration_ms, pitch, velocity}` in milliseconds, not beats, because the cut is in milliseconds and `cueSeconds` is the length contract. Film Engine validates it (length against `cueSeconds`, pitch/velocity ranges, GM program set), writes an SMF with a hand-rolled writer, and registers it as `film_assets` `other` + `metadata.kind='midi'` linked from the cue. No renderer yet: a MIDI file is already useful to the DAW package (MUS-015) and to anyone with Kontakt open. Measure it on `tests/fixtures/thirty-second.fountain` and on the diner scene; if the agent cannot write a usable 202-second underscore, stop here and record why — that is the bet, and it is cheap to lose.

**Phase 2 — notes become sound (one declared binary, open libraries).** `lib/instrument-render.js` with a resolver in the `resolveFfmpeg` shape; a `music` adapter (`sfz-render` or `fluidsynth`, id chosen by what resolves) whose `generate('music', payload)` throws `PRECONDITION` without a MIDI asset, so the orchestrator records a skip rather than retrying. Self-hosted, priced at zero *explicitly* in `provider-pricing.js`, on the Gridlight precedent. FluidSynth first (active, LGPL, Homebrew), sfizz second (better orchestral SFZ, but archived June 2026 — say so in the adapter's `reason`). Ship VSCO 2 CE (CC0) as the default orchestra and FluidR3 (MIT) as the GM fallback, as operator-installed paths, never bundled (3 GB). Verify every render by **reading the file back** — duration within one frame of the cue, peak above silence — because the stitcher's audio was −91 dB for months while every "is there a stream" check passed.

**Phase 3 — optional Kontakt.** Only if Phase 2 output is used in a real cut and the timbre is the complaint. Prefer architecture **D** (REAPER) over **C**: it is the host Kontakt is tested against, it is one resolvable executable rather than a compiled GPL host we maintain, and its project file is text. Treat it exactly as the conform treats ffmpeg — an executor probed at runtime, reported when absent, never assumed.

**Explicitly not worth doing:**
- Joining the NKS partner program. It is for shipping instruments into NI hardware; it gives nothing to a consumer of instruments.
- Automating Native Access or reverse-engineering NI's licensing. Fragile, EULA-adjacent, and a GUI login is a one-time act per machine.
- A Python sidecar (Pedalboard/DawDreamer) as the production renderer. It is the right tool for a one-off experiment on the director's Mac and the wrong dependency for this backend.
- Building an in-engine synthesizer or sampler. FluidSynth is the answer to that and it is thirty years old.
- Widening the `film_assets.asset_type` CHECK for `midi`. The 3D work already recorded why not.

## Open questions for the user

1. **Do you own Komplete, and which libraries?** Kontakt 8 full ($299) vs Player (free) decides whether third-party non-Player libraries are even loadable; Komplete's factory content decides whether Phase 3 is worth more than VSCO.
2. **Is the render machine always this Mac?** Native Access activation and the three-device rule mean yes for Kontakt; Phase 2 has no such limit.
3. **Which ElevenLabs plan, and what does its Music Commercial Rights table say about film?** This is the one fact that could move Phase 2 from "nice" to "necessary". Read the primary table; two secondary sources say self-serve excludes film/TV.
4. **Is "editable notes" the goal, or "sounds like real instruments"?** Phase 1 answers the first with no renderer; sections + ElevenLabs may already answer the second well enough.
5. **Does the agent compose whole cues or parts?** Whole-cue MIDI from an LLM is the unproven step; per-track parts over a fixed harmonic plan (the way MIDI Agent frames it) may be the honest scope.
6. **Should `stock` come back?** Separate question (SHIP-030), but a catalogue with an agreement-gated API is the cheaper route to *cleared* music and should not be conflated with this one.
7. **Is REAPER acceptable as a paid, user-installed executor?** It is the ffmpeg pattern with a licence fee; if not, Phase 3 becomes a compiled JUCE host we own.

## How this would be tested

Set-based over the registries it touches, in the repo's style — never a hand-typed list of the new pieces.

- **`CAPABILITIES` (`providers/base.js:42`).** If MIDI composition becomes a capability (served by the agent host the way `llm` is, spending nothing), the existing load-time guards must already accept it: `flow-cost.js:42` throws without a `COST_PER_CALL` entry; `provider-pricing` and `ai-spend.test.js` iterate `providers.list()` × capabilities and fail an unpriced pair; `provider-tiers.test.js` requires every adapter to declare its contract; `dry-run.test.js` requires every capability to describe its request. Adding `midi` is a twelve-registry change (the `world` write-up in CLAUDE.md lists them); the test is that the server boots and every derived denominator grew by one.
- **`PIPELINE_STEPS` / `MEDIA_KINDS`.** A `midi` step, if orchestrated, is `scope: 'scene'` like `music` and `music` gains `depends: ['midi']` only when the render adapter is selected — `phase0-payload-parity` and `pipeline-scope.test.js` derive from these and will demand a payload builder and a scope gate. `MEDIA_KINDS` gets a `midi` entry with `assetType: 'other'` and the importer test (`media-imports.test.js`) must accept a hand-made `.mid` upload at the same target, because a composer with a DAW is the first person who will want to skip Phase 1.
- **Preflight stages (`e2e-preflight.js`).** The render binary is an `externalDependency` beside `assembly: 'ffmpeg'` (`:64`); `e2e-readiness.test.js` and `e2e-first-film-plan.test.js` derive the stage list and fail a plan that does not name it. `checkConformDependency` gets a sibling and `ffmpeg-consumers.test.js`'s rule — every consumer reads the fields the resolver actually returns — applies to the new resolver by construction if it returns the same `{ available, bin, source, reason }` shape.
- **Render validity, behaviourally.** Like `conform.test.js`: write a two-note MIDI, render it, read the file back with `inspectMedia`, assert duration equals the cue's `cueSeconds` within one frame and peak level is above silence. A mutation that swaps the SoundFont path for a missing one must fail on volume, not on exit code.
- **MCP parity.** `mcp-tools.test.js` already fails a route with no tool and a tool with no route; `mcp-no-server-llm.test.js` must stay green — the composition tool hands the brief out and stores a note list, it never calls a model. `music-cue-mcp.test.js`'s rule ("an agent can write the direction, not only press generate") extends to: an agent can write the notes.
- **Rights.** Every rendered asset is `license_source: 'generated'` today (`music-gen.js:244`, `:713`); a sample-rendered file should record the *library's* licence (`cc0`, `mit`, `ni_eula`, `third_party`) in metadata so the rights report (migration 038) can say what a cue is made of. Test: for every library the resolver can find, the registered asset names a licence, and an unknown library is refused rather than recorded as generated.
